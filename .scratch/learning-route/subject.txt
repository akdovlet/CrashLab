Résumé
CrashLab est un projet de microstructure de marché. L’étudiant construit deux exchanges locaux de
type bucket shop, fait trader une population d’agents, implémente un perpétuel BTC/USD avec levier,
puis compare deux modèles de liquidation. Binance n’est utilisé que comme oracle public de prix :
aucun carnet, volume, trade, open interest ou ordre Binance n’entre dans la simulation.

Le projet doit montrer qu’un moteur de matching peut être techniquement correct tout en produisant
un risque systémique si son mark price est mal conçu.

    Règle centrale
    Tous les ordres, carnets, trades, positions, liquidations, frais, volumes et métriques sont produits
    localement. Binance fournit uniquement un point d’ancrage public BTC/USDT en lecture seule.

 Élément                       Exigence

 Produit principal             BTC-USD-PERP linéaire, réglé en unité de cotation simulée

 Exchange A                    C++17 + Simplx, performance-first, mark price fragile

 Exchange B                    Python 3.12 + asyncio, mark price robuste ancré sur l’oracle

 Population                    200 agents minimum, 1 000 pour le benchmark

 Couverture                    50 % minimum sur le code testable

 Sécurité                      Aucun ordre réel, aucune clé API de trading, aucune identité réelle

1. Préambule
Un bot de trading sans marché crédible apprend surtout à exploiter les défauts de son propre
simulateur. Ici, l’ordre est inversé : on construit d’abord le marché, le ledger et le risque ; les stratégies
arrivent ensuite.

Le projet est volontairement ambitieux. Il doit être mené par étapes, avec un système exécutable à la
fin de chaque jalon. Une fonctionnalité sophistiquée n’a aucune valeur si le carnet, les comptes ou le
replay ne sont pas déterministes.


Objectifs pédagogiques
●
    Comprendre la priorité prix-temps, les ordres limites, les ordres marché, les annulations et les
    exécutions partielles.
●
    Distinguer reference price, local mid, last traded price, index price et mark price.
●
    Implémenter la marge initiale, la marge de maintenance, le levier, le funding et les liquidations.
●
    Observer les effets collectifs : crowded trades, retrait de liquidité, cascades et arbitrage
    cross-exchange.
●
    Mesurer PnL, slippage, drawdown, VaR, latence et coût d’exécution.
●
    Comparer une architecture actor-based C++ et une architecture async Python.


Ce que ce projet n’est pas
     Interdit
     Le projet ne doit jamais envoyer d’ordre à Binance ou à une autre plateforme réelle. Il ne doit
     contenir aucune clé API de trading, aucun capital réel et aucune donnée d’identité réelle.


Il ne s’agit pas non plus d’un concours de PnL. Une stratégie profitable sur un moteur incorrect obtient
moins de points qu’une stratégie médiocre sur un système réconciliable, testé et mesuré.

4. Les prix du système
Le projet doit exposer clairement quatre notions. Toute confusion entre elles est une erreur de
conception.

 Prix                   Origine                                     Utilisation

 Reference price        Oracle public Binance, lecture seule        Fair value externe, contrôle de divergence, mark
                                                                    robuste

 Local mid              Meilleur bid/ask du carnet local            État de la liquidité locale

 Local last price       Dernier trade local                         Historique, affichage, mark fragile de A

 Mark price             Règle propre à chaque exchange              PnL non réalisé, marge et liquidation



Exchange A : modèle fragile
mark_price_A = local_last_traded_price_A

Le matching engine de A doit être correct. Sa faiblesse est économique : un trade local isolé peut
déplacer le prix utilisé pour la marge.


Exchange B : modèle robuste
premium_B = EMA(local_mid_B - reference_price)
mark_price_B = reference_price + clamp(premium_B, -max_basis, +max_basis)

B autorise une petite prime ou décote locale, mais empêche un trade ponctuel de déclencher
immédiatement une liquidation générale.


États de l’oracle
 État                      Comportement obligatoire

 LIVE                      Trading normal.

 STALE                     Réduction de risque autorisée ; augmentation de risque configurable ou refusée.

 DISCONNECTED              Market maker retire ses quotes ; nouvelles positions à levier bloquées.

 REPLAY                    Temps contrôlé par le scénario ; aucune dépendance réseau.

    M4. Perpétuel, levier, marge et liquidations                                                     15 pts

Le produit principal est un perpétuel linéaire local :
symbol            = BTC-USD-PERP
contract_qty      = BTC
settlement        = USD simulé
funding_period    = temps simulé configurable
tick_size         = configurable

Formules minimales
notional = abs(position_btc) * mark_price
initial_margin = notional / leverage
unrealized_pnl = position_btc * (mark_price - avg_entry_price)
equity = wallet_balance + unrealized_pnl
maintenance_margin = notional * maintenance_margin_rate

Déclenchement :
equity <= maintenance_margin + estimated_liquidation_fee

●

●
    Les ordres de liquidation passent par le matching engine comme les autres ordres.
●

●
    Les pertes résiduelles alimentent un mécanisme d’assurance simulé et tracé.
●
    Le mark price de A et celui de B doivent être calculés indépendamment.

Funding local
premium = (local_perp_mid - reference_price) / reference_price
funding_rate = clamp(k * premium, -max_funding, +max_funding)
funding_payment = position * mark_price * funding_rate

Un market maker global cote simultanément A et B. Il est un compte normal doté de limites importantes

fair_value = reference_price

            + latency_component
            + risk_component

●

●
